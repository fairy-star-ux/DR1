# 执行测试步骤

对象：DR1M90 当前 Linux + FPGA Web 控制版本。测试日期、源码 commit、镜像 SHA-256、接线和结果应记录在一次独立测试日志中。
本文件中的命令只有手工执行才会驱动设备；仓库默认检查不触发运动。

## 0. 测试前提

1. 核对《硬件接线》，电机/舵机电源和地；电机先架空、保证可直接断电。
2. 首先确认 SD `BOOT.bin` 已包含此版本舵机位流。未确认前保持 FPGA MMIO 配置关闭。
3. 不同时运行旧 `boat_main`、串口终端和 Web 争用串口；拍照工具也不能同时独占摄像头。
4. 将 `BOARD_IP` 替换为板子实际地址。当前实验曾使用 `192.168.137.100`，不是所有网络的固定值。
5. 打开串口终端，参数 115200、8N1，保存完整冷启动日志。

## 1. 仓库离线检查（电脑/虚拟机）

```bash
python3 scripts/check_repo.py
python3 -m unittest discover -s tests -v
```

预期：TD 引用文件存在、无凭据/编译产物混入源码、Python 可解析，NMEA 和 API 参数等离线测试通过。
这些结果不代表真实串口、AXI、摄像头或机械动作已经通过。

## 2. Linux 启动与 USB

```sh
uname -a
cat /proc/cmdline
mount
ls /dev/ttyUSB* /dev/video* 2>/dev/null
lsusb
lsmod
dmesg | tail -60
cat /proc/tty/driver/serial
```

预期：root 为 SD 第 2 分区 ext4；USB 转串口由 CH341 绑定；摄像头有 UVC Capture 节点。
出现 `/dev/ttyS1` 但 `uart:unknown` 不算可用 UART。`lsusb` 有设备但没有 ttyUSB 时查 CH341 模块、供电与 USB 断连。

```sh
modprobe ch341
ls -l /lib/modules/$(uname -r)/modules.dep
```

`modprobe` 报模块不存在时先检查 rootfs 是否漏安装模块；不要混用其他内核编译的驱动。

## 3. WiFi 和网络

```sh
ip -4 addr
ip route
ls /sys/class/net
ps | grep '[w]pa_supplicant'
dmesg | tail -60
```

确认 WiFi 有关联及局域网 IP；以太网与 WiFi IP 可能不同。WiFi 不通时看 `S40aic-wifi` 日志、固件目录、nl80211 后端和 DHCP。
网线直连可临时配置（先确认电脑网段，避免冲突）：

```sh
ip link set eth0 up
ip addr add 192.168.137.100/24 dev eth0
```

临时命令不解决开机持久化；使用 SDK 的 dhcpcd/network 配置保存静态设置，并避免两个 DHCP 客户端抢同一接口。
如果管理 SSH 正走 eth0，不要不加核对地 flush 该网卡地址。

## 4. Web 启动和只读状态

```sh
/etc/init.d/S99boat-web restart
tail -30 /var/log/boat-web.log
wget -qO- http://127.0.0.1:8080/api/status
```

电脑：

```bash
python3 scripts/check_board.py http://BOARD_IP:8080
```

浏览器打开 `http://BOARD_IP:8080`。预期页面有电机速度、GPS、照片、云台两轴和超声波舵机控制。
`servo_control=true` 只说明配置允许 MMIO，不代表自动识别了正确位流；先核对启动镜像。

## 5. GPS（先证明接收，再证明定位）

Web 正常时直接看 `/api/status`：`available=true`，定位后应 `fix=true` 并有经纬度。
需要独占串口检查时：

```sh
/etc/init.d/S99boat-web stop
stty -F /dev/ttyUSB1 9600 raw -echo -ixon -ixoff -crtscts
timeout 8 cat /dev/ttyUSB1
/etc/init.d/S99boat-web start
```

预期收到 `$GNGGA`、`$GNRMC` 等 NMEA 行。GGA 定位质量 0、RMC 的 V 都是未定位，不能标为 GPS 已定位。
室内没有 fix 与串口收不到数据是两类问题；不要靠修改串口驱动来解决搜星问题。

## 6. 摄像头实时预览和拍照

打开网页摄像头区域，应自动显示实时画面；可使用“关闭预览”和“开启预览”。实时接口为 `GET /stream.mjpg`，采用 MJPEG 640×480，每个浏览器连接最多约 10 帧/秒。
移动镜头前的物体确认画面变化，再保持预览点击“拍照”，应正常保存并显示在图库中。多标签页与拍照共用一个采集进程，不应各自独占摄像头；实时画面本身不持续写入 SD 卡。
首次连接会丢弃前 11 个有效帧等待曝光稳定。关闭浏览器预览后后台仍维持采集；需要独占运行诊断工具时先停止 Web 服务。
清空图库前备份需要保留的照片，点击“清除全部照片”并确认，检查图库清空；该操作删除板上已保存照片。

先单独拍照，测试时场景应有光且镜头无遮挡：

```sh
/etc/init.d/S99boat-web stop
timeout 20 /usr/local/bin/camera_capture /dev/video0 /tmp/manual.jpg
echo $?
ls -lh /tmp/manual.jpg
/etc/init.d/S99boat-web start
```

返回 0 且生成文件后，还要打开照片确认内容，不以文件大小代替图像质量验收。
工具使用 MJPEG、MMAP，丢弃若干帧等待曝光；某些摄像头不支持对应控制，警告不一定是致命错误。

在电脑测试 Web（连续 3 次，间隔至少 2 秒）：

```bash
curl -X POST http://BOARD_IP:8080/api/capture
curl http://BOARD_IP:8080/api/photos
```

打开返回的 `/photos/文件名.jpg`，应显示正确场景；板上路径 `/var/lib/boat-web/photos/`。
重启后照片仍存在才算持久化通过。黑图、超时、USB 断连分别记录；先停其他采集进程，再排查 Hub 和供电。

## 7. 舵机控制（确认匹配位流后）

在 `/etc/default/boat-web` 设置 `FPGA_SERVO_MMIO_BASE=0x80010000`，重启 Web。
电脑执行：

```bash
curl -H 'Content-Type: application/json' -d '{"pan":80,"tilt":90}' http://BOARD_IP:8080/api/ptz
curl -H 'Content-Type: application/json' -d '{"pan":100,"tilt":90}' http://BOARD_IP:8080/api/ptz
curl -H 'Content-Type: application/json' -d '{"pan":90,"tilt":80}' http://BOARD_IP:8080/api/ptz
curl -H 'Content-Type: application/json' -d '{"pan":90,"tilt":100}' http://BOARD_IP:8080/api/ptz
curl -H 'Content-Type: application/json' -d '{"angle":60,"enable":true,"sweep":false}' http://BOARD_IP:8080/api/ultrasonic
curl -H 'Content-Type: application/json' -d '{"angle":120,"enable":true,"sweep":false}' http://BOARD_IP:8080/api/ultrasonic
curl -H 'Content-Type: application/json' -d '{"angle":90,"enable":true,"sweep":true}' http://BOARD_IP:8080/api/ultrasonic
# 观察一个往返周期后停止：
curl -H 'Content-Type: application/json' -d '{"angle":90,"enable":false,"sweep":false}' http://BOARD_IP:8080/api/ultrasonic
```

验收：响应 ok、实际三路各自运动且方向正确、扫描可停止，`dmesg` 无 SError。
若机构限位不足，不运行全程扫描。不要在出错后不断重复写总线；禁用 MMIO、恢复对应镜像并重新核对。

## 8. 两电机：仅运行 3 秒

电机测试使用已验证驱动协议 `$pwm:3000,0,3000,0#`，对应两轮通道 1 与 3。
先在网页发送全 0；如果驱动板需要电机类型/死区初始化，使用串口诊断工具并核对驱动板型号。

电脑执行（保持现场可断电）：

```bash
curl -H 'Content-Type: application/json' -d '{"pwm":[3000,0,3000,0]}' http://BOARD_IP:8080/api/motor
sleep 3
curl -H 'Content-Type: application/json' -d '{"pwm":[0,0,0,0]}' http://BOARD_IP:8080/api/motor
```

然后分别测试网页手动 PWM、前进/后退与两轮差速，低幅度起步。
验收须观察真实两轮旋转与停止；网络中断会让客户端停止命令无法送达，当前版本没有失联自动停车保证。
`linux/tools/motor_test.c` 会发送 mtype、deadzone 并运行 3 秒，不能与 Web 同时争用串口。

## 9. 持久化验收

1. 停止电机和扫描，保存镜像哈希与日志。
2. `sync; reboot`，确认 SSH/Web/WiFi 自动恢复，无需手动 PROGRAM_SRAM。
3. 重复步骤 7 的小角度测试，确认寄存器写入和实际动作。
4. 停止电机与扫描、`sync; poweroff`；确认系统关闭后断电，再上电，做同样验证。
5. 检查历史照片保留、默认扫描状态关闭、串口映射仍正确。

SSH 重启测试与断电冷启动测试必须分开记录。不能仅凭一次 API 成功宣称整套硬件冷启动已验收。
